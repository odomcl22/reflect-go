## Qualification limits

The development host is an Apple M1 with 16 GiB RAM. The new per-layer sliding-window profiles pass metadata screening at 16,384 and 49,152 tokens using a simulated 48 GiB Mac memory ceiling. Neither large Starter Pack
model has been loaded on a 48/128 GiB host during this release preparation.
Checksum verification does not establish task quality or performance.
Gemma/Muse estimates follow the pinned runtime’s single-slot SWA allocation, including ubatch 128 and 256-cell padding, per-layer KV heads, local/global head dimensions, conservative widest-layer V-row padding, and the existing 50% cache margin. Unknown metadata still uses the generic fallback; long contexts without validated attention metadata remain blocked. On Macs with at least 32 GiB, the memory ceiling reserves a
quarter of physical memory for the OS; smaller Macs keep the half-RAM ceiling.

Native desktop visual automation is disabled in the current session. No new
desktop UI end-to-end result is claimed. Historical native app evidence is in
[0.4.8 validation](PREVIEW_0_4_8_VALIDATION.md); it does not qualify Gemma/Muse.
Windows/Linux physical-device execution and the PowerShell download helper
still require testing on those systems. Cross-compilation is reported separately
from execution testing.

## Sliding-window memory reference

Source: llama.cpp commit `7fe450e19305b828c199d602c23a8337aaa1f03b`, `src/llama-kv-cache-iswa.cpp` and `src/llama-kv-cache.cpp`. The SWA cache uses `pad256(min(base_cells, sliding_window + ubatch))` for one slot. Reflect Go does not enable full-size SWA or inherit host runtime flags. Synthetic metadata regression tests and the two actual GGUF headers agree. Estimates at 16K/49K: Gemma 26.65/25.16 GiB; Muse 21.72/21.58 GiB. The smaller long-context estimate reflects the Q4 cache selected above 32K. These are estimated allocations, not measured resident memory or physical 48 GiB execution.
